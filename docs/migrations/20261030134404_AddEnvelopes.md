# Migration: AddEnvelopes (RECEIPTS-1082)

**Migration id:** `20261030134404_AddEnvelopes`
**Date:** 2026-10-30

Take a portable backup before deploying this migration.

## What it does

The schema migration:

- creates the `budget` schema with `Envelopes`, `Occasions`, `ItemTypeEnvelopeDefaults`
  and the singleton `EnvelopeBackfill` marker, plus `ynab.YnabEnvelopeMappings`;
- adds `EnvelopeId`, `EnvelopeSource` and `OccasionId` to `receipts.ReceiptItems`, and
  `PaidFromEnvelopeId` and `OccasionId` to `receipts.Receipts`. Existing items get
  `EnvelopeSource = 'Historical'` and no envelope;
- replaces `matching.refresh_normalization_revision()` so an update that changes only
  those five columns keeps the row's normalization revision. Budget attribution is not
  normalization or classification evidence, the same reasoning as the canonical
  embedding exemption in `IsolateCanonicalBusinessRevision`.

## The data step

`DbMigrator` runs the envelope backfill right after `MigrateAsync`, in its own
transaction, once per database (`EnvelopeBackfill.RunIfPendingAsync`). It runs only
when there is no marker and the database has historical items or node-keyed YNAB
mappings, so a fresh install stays untouched (and remains a pristine restore target).
The deploy log reports counts only.

The plan comes from `EnvelopeBackfillPlanner`, which reuses the retired resolution
code, `ExternalCategoryMappingPolicy.ResolveRecorded`, so parity holds by construction:

1. For every item (trash included) and every budget with node mappings, resolve the
   YNAB category exactly as push did: the nearest mapped ancestor of the item's current
   assignment, along its recorded path.
2. Group items by the resulting set of (budget, YNAB category) pairs. Each distinct set
   becomes one active envelope, named after its YNAB category (the selected budget's
   name when it has one), with those YNAB links. With one budget this is one envelope
   per distinct mapped YNAB category.
3. An item that resolves to nothing but has a classified root gets one **archived**
   envelope per such root, named after the root. These envelopes have no YNAB link, so
   those items stay unmapped, as before.
4. Unclassified items keep no envelope. They take their type's default when classified.
5. Each mapped item type seeds `ItemTypeEnvelopeDefaults` with the envelope its current
   resolution reaches, so future purchases keep today's behaviour.
6. A legacy mapping row with no stable category (an ambiguous legacy name) never
   resolved for push. Its YNAB category still becomes a linked envelope with no items,
   so the owner's choice is not lost.

Every name comes from data. A repeated name gets a ` (2)`, ` (3)` suffix. Items get
source `historical`.

## Parity check

**Invariant:** for every item and every budget, the YNAB category reached through the
item's envelope equals the one its recorded classification reaches through the node
mappings. `EnvelopeParity` checks it; unit tests check it over generated trees.

Run it against a database (read-only, counts only):

```sh
RECEIPTS_MIGRATION_CONNECTION='Host=…;Database=…;Username=…;Password=…' \
  dotnet run --project tools/Receipts.EnvelopeParity
```

It prints item, envelope and budget counts, how many items each path maps, and the
mismatch count, and exits 2 when any item mismatches. Run it straight after the
migration: later classification changes legitimately move `default`-sourced envelopes.

## Rollback

`Down` restores the previous revision trigger and drops the new tables and columns,
which discards every envelope, occasion, default and link recorded since. The frozen
`ynab.YnabCategoryMappings` rows are untouched, so redeploying replays the same
backfill. Pair a rollback with reverting the code.

## Limits

- The legacy in-place taxonomy procedure (`tools/Receipts.TaxonomyMigration`) assigns
  classifications after DbMigrator has run, without going through `AppendAsync`. On a
  database that still needs that procedure, the envelope step finds no classifications,
  so its items keep no envelope and fail closed as unmapped at push. Restore such data
  from a portable backup instead, which derives envelopes after the taxonomy conversion.
- Restoring a portable backup older than format 15 derives envelopes the same way,
  and requires a destination without envelopes.

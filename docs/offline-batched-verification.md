# Offline bounded verification experiment

This opt-in candidate extends the exhaustive shortlist into deterministic verification batches. It has no transport, credential access, registration, or production activation. Existing `Plan`, `ExhaustiveShortlist.Prepare`, and `CandidateWire.Prepare` behavior remains available.

Use `ExhaustiveShortlist.PrepareForBatchedVerification`, aggregate every shortlist response, then pass its verification plan to `BatchedVerification.Prepare`. Alternatively, `SupportedCategoryCandidate.PlanForBatchedVerification` accepts an explicit complete candidate set. The experimental limit is 128 unique nodes after ancestor closure. Every plausible terminal and every ancestor survives; overflow abstains or fails instead of selecting top candidates. The .3/.7 thresholds and existing supported-path reducer are unchanged.

Each path receives separate support and context questions. Path requests hold at most 32 complete paths, and the 32 KiB UTF-8 request bound may split them earlier. Version 2 partitions the complete canonical taxonomy into bounded coverage requests. Each taxonomy node appears exactly once as a coverage subject; each request also carries the full definitions of all ancestors needed by its subjects, the complete verified category ID union, and complete purchase evidence. Ancestors may repeat as context. Each partition independently asks whether any plausible subject is absent from that union. Nothing is ranked, pruned, or truncated. An individual alternative, its ancestors, or a complete support/context path that cannot fit causes terminal planning failure.

All responses, including every coverage partition, must arrive exactly once in request order. Strict schemas reject omitted, repeated, unknown, cross-plan and malformed answers. No batch produces an early winner. The maximum coverage answer is passed to the existing reducer solely as a logical all-partitions guard: every partition must be at or below the existing rejection threshold. This maximum is **not a calibrated probability of the union**. A positive or uncertain partition blocks assignment; missing or invalid responses fail. Purchase evidence is asked once, in the first coverage partition. Existing path support/context requests and .3/.7 thresholds remain unchanged.

Question IDs bind the exact immutable purchase, taxonomy, revision, model, complete paths, questions, policy and batching format. Input order is canonicalized for the opt-in plan. Usage is validated and summed with overflow checks; usage does not establish accuracy or context fit.

The byte guard is not a token counter. Before a separately authorized transport uses these artifacts, a pinned-model tokenizer must count the complete requests (including the model's actual serialized input) with an input allowance that reserves output/context overhead. `ValidateInputTokenBudget` checks every artifact against a caller-supplied tokenizer and positive budget; it does not implement or certify that tokenizer. This offline experiment does not establish model context fit, latency, cost, or classification quality. No held-out examples or thresholds were tuned.

Synthetic tests cover 70 terminals with 112 closure nodes, deterministic ordering, complete union coverage, cross-root conflicts, ancestor fallback, missing/duplicate/cross-plan/malformed responses, closure overflow, byte overflow and the explicit token-budget check. A controlled live evaluation and any runner integration remain separate work.


The paired C# replay format is version 2 and rejects a complete plan requiring more than 30 total requests (production, exhaustive shortlist and every verification partition). Failure never shortens the alternative set. Offline synthetic validation includes a 309-node taxonomy exceeding 40 KB, exact subject ordering and union, repeated complete ancestor definitions, positive/uncertain alternatives in every partition, and incomplete or malformed coverage vectors.

Python stage/live integration remains an explicit gap: its current ledger schema permits at most five verifier batches and exactly one final coverage flag. These version 2 multi-partition plans must not be used with that integration until its schema, reopening checks and tests support them. The existing 512 KiB verifier-record and 2 MiB ledger limits, and authorized 30-call cap, have not been expanded. No provider requests, credential access, private data, activation or threshold tuning were performed.

Before exposing initial requests, the paired constructor reserves at least two of the 30 slots for a path request and coverage. It rejects oversized initial vectors immediately. The exact complete verifier vector is independently checked against the remaining slots before export; extra byte-driven partitions cause terminal failure rather than an extra request.

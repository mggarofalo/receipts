# Realtime connection recovery

`useSignalR` owns one SignalR connection for each enabled effect and authenticated session. SignalR handles reconnecting an established connection. If initial startup fails, or SignalR exhausts automatic reconnect attempts, the hook retries while mounted with delays of 1, 2, 4, 8, 16 and then 30 seconds. The delay stays capped until a successful connection resets it. A single timer and in-flight start guard prevent overlapping manual starts; the hook starts only a natively disconnected connection.

The connection ID is cleared when reconnecting begins and published only for a current, natively connected lifetime. Publication precedes cache catch-up so new HTTP requests carry the current origin header. A successful initial start, manual restart or automatic reconnection invalidates the deduplicated union of the shared domain projection policy. This repairs changes missed between an earlier read and connection establishment, including dashboard queries with infinite freshness. Before invalidation, catch-up cancels supported reads still in flight: TanStack can reuse active first reads, and inactive reads can continue after navigation. Either old result could clear staleness and remain fresh indefinitely. After cancellation it rechecks the current session and native connection before refreshing. Active views refetch and inactive queries become stale. Catch-up produces no mutation toast and does not imply that every read succeeded.

Catch-up represents unknown missed changes. It is distinct from a known template-created event, whose deliberate similarity-cache exception remains in the ordinary event policy. The union includes restored YNAB configuration after backup import coverage, so active integration queries may consult YNAB. It excludes authentication and administrator query state. Domain producers absent from the shared policy still need their own coverage; a connection is neither a durable event log nor proof of complete application freshness. Optional integration-read error presentation is owned separately.

`api-config.ts` supplies the same API base for HTTP requests, token refresh and the hub. It removes trailing slashes and preserves a configured reverse-proxy path prefix. An empty base keeps same-origin paths. This URL composition does not change server CORS or authentication policy.

`token-refresh.ts` owns one pending refresh per session and refresh-token family, shared by HTTP and SignalR. The hub's async token factory refreshes tokens whose numeric finite expiry is missing, malformed or within 30 seconds. Expiry inspection is a scheduling hint; the server validates credentials. Refresh writes still require the captured session and refresh token to match. A hub refresh failure fails that connection attempt and permits retry without logging out during a network outage. Existing HTTP terminal authentication handling remains authoritative.

Cleanup first makes the lifetime inactive, cancels its retry timer and token wait, removes its event handler and session subscription, and stops the owned connection. Cancelling a hub wait does not cancel a shared refresh needed by an HTTP caller. Old callbacks and late startup completions cannot publish state, origin IDs, cache invalidations or toasts into a replacement session.

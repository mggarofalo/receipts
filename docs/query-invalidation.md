# Query projection ownership

The client uses `src/client/src/lib/query-invalidation.ts` to map domain changes to query prefixes. Read hooks use the same typed prefixes without changing their existing cache identities. Successful ledger, account/card and suggestion mutations and corresponding SignalR notifications apply this policy to the current provider's QueryClient.

Receipt items, transactions and adjustments affect more than their own lists. Their shared ledger policy refreshes receipt aggregates, trips, reports, dashboard ranges and totals, history-based suggestions and template candidates, normalization usage views, and receipt-derived YNAB views. Invalidating the dashboard prefix also refreshes the earliest-year query despite its infinite freshness setting. Active observers refetch; inactive entries become stale and refetch when observed. Components need no additional cache repair after invoking these mutation hooks.

The policy avoids invalidating unrelated YNAB budgets/accounts/categories after an ordinary ledger edit. This does not promise zero remote reads: refreshing split comparison can itself consult YNAB categories and transactions. Card/account changes also refresh mappings and stale-mapping diagnostics because a card merge can remove source accounts and their mappings. A no-op card merge retains its existing no-invalidation behavior.

Category and subcategory changes refresh suggestion lists, including category cascades. Template updates/deletions refresh template, canonical-registry and similarity queries. Template creation refreshes templates and the registry but deliberately retains similarity/recommendation caches until their normal freshness expires: a promoted template may lack its embedding and temporarily rank below its former history suggestion. Local creation/promotion and remote created events share this exception. None of these operations rewrites historical category labels or receipt prices. Trash purge applies the union of the domain changes it produces.

The report's grouped categorization operation belongs to `useCategorizeReceiptItems`. Different receipt groups can commit independently. It observes and awaits every request, then repairs projections on settlement even if one group failed. The caller still receives the failure and retains its selection. Optimistic delete hooks retain cancellation, snapshots and rollback; their settlement invalidation refreshes the authoritative result after success or failure.

`useMergeAccountMaintenance` owns the merge dialog's account cleanup and retry rename requests. It retains caller-owned error handling instead of registering new global mutation errors. Its callbacks have stable identities and check the captured session before a request and after either success or failure. The dialog retains its cleanup warning and retry flow; the hook owns successful account cache repair. Account-card summary memoization includes every projected field so a refetch with unchanged membership can still update card names and codes.

SignalR invalidates before classifying the notification's toast origin. An event from the same connection therefore repairs data while suppressing its duplicate toast. Account events use the same policy as local account writes. Existing session guards reject old-session callbacks, and the helper never selects a global QueryClient. Cache invalidation is not the session boundary or a durable event log.

This hardening covers ledger/account/card, taxonomy/template, purge and backup-import producers. Synchronous normalization/YNAB/report producer coverage and background worker completion require the subsequent RECEIPTS-948 work; their freshness is not established by centralizing the existing event map. Successful initial connections and reconnections now cancel supported in-flight reads and refresh the supported domain union; see [Realtime recovery](realtime-recovery.md) for retry, token and session ownership. No global query-cache clearing or authentication/admin-query refresh is implied by these domain changes.

Backup import uses `invalidateAfterBackupImport` for both local success and its remote event. Like reconnect, it cancels supported in-flight reads before invalidating, including inactive reads that survived navigation. Their old results must not clear staleness after restore. Its union includes all restored domains and the entire YNAB root because import can replace destination settings. A single prefix-union predicate refetches each active query once even when parent and child prefixes overlap. The asynchronous continuation checks its session/lifetime again after cancellation; local repair does not require a connected hub. See [Backup & restore](backup-restore.md) for the committed notification boundary and transfer ownership.

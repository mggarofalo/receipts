# v14 review protection: integration design

Public export and import now use complete v14 archives through the validated automatic-history and saved-review codec. Legacy v13 archives remain importable. The long-running API host now runs deterministic approved-mapping reuse alongside the Classification workspace's automatic activity and conditional undo surface. It does not call a provider; Jev automatic classification remains unimplemented. The design below records the original integration requirements, including the worker-disabled rollout stage; it is not a completion checklist or a description of current worker activation.

The current disposition is actor-private and keyed by the exact historical group; its null state is also meaningful because it retains a version for reopening and optimistic concurrency. Capture actor, exact group, nullable state, version, operation ID and update time; verify the stored source hash against the exact group. Preserve all rows, including null state. No historical disposition operation log is needed for current state, but restoring without it changes retry semantics: either transfer the matching operation record and validate it against the current row or explicitly reject colliding operation IDs and document the retry boundary. Do not synthesize a log entry.

Assistance review rows are keyed by actor and attempt and have a restrictive FK to an operational attempt. Capture actor, opaque original attempt ID, canonical source from the joined attempt, state, revision, and sorted exclusions. Include active rows too: their exclusions protect individual items. Retain distinct rows per actor and attempt, even for the same source; collapsing them can lose independent decisions. Do not transfer the attempt, provider result, request, job, connection or consent. The new durable review-protection table needs these fields and a unique `(Actor, AttemptId)` key, without an attempt FK; it must support review of the preserved state by its owner independently of the old suggestion. Store and compare the existing revision. A user must be able to reopen or change that record, including removing exclusions, through a source-based review surface; merely adding an invisible executor guard strands the decision.

Capture both sets in the existing repeatable-read backup snapshot. Write a required v14 SQLite archive table with separately tagged records and strict, explicit required fields; validate unique identities, canonical source, state, revision, exclusion size/order/uniqueness, exact group hash and valid business item references before destination mutation. Preserve deleted or changed item identities as historical exclusions rather than inferring current eligibility. Reject malformed or contradictory archive records. Actor IDs are portable opaque scopes: never replace an unknown actor with the restoring user, and do not require an Identity user to exist on the target.

Under the existing import transaction and normalization write gate, preflight the union with destination state before any writes. Do not overwrite a destination decision based only on a version or timestamp: independently evolved rows can share versions or revisions. Accept identical identity and contents as replay; reject divergent collisions atomically. Preserve unrelated destination protections. For disposition rows, also detect `(actor, source hash)` collisions and exact source mismatch, ID and operation-ID collisions. For assistance projections, require identical contents on an existing `(actor, attempt ID)` or reject. Include all rows already present in the new table in future exports, as well as current attempt-backed rows; reject conflicting duplicates rather than choose one. Define a migration or transactional dual-write so updates to live attempt preferences and portable rows cannot diverge.

Executor and discovery must consult both existing attempt-backed preferences and the durable projections. Keep the existing source-wide rule: any actor's `later` or `left_as_is` source preference protects every item for that source, while an active preference protects its excluded items. Dispositions retain their current actor scope and exact-source matching. The write gate must serialize preference updates and restore with historical execution. Discovery triggers must mark affected sources dirty when durable preferences change. New source-based update operations must use concurrency revisions and idempotence without requiring or recreating an attempt, and must not introduce extra pending suggestions or provider work.

Before enablement, exercise actual PostgreSQL and SQLite end-to-end capture, fresh restore and replay; both state variants, exclusions, reopening, concurrent execution/update/restore, source and actor scope, missing actor, existing destination conflicts and rollback, altered SQLite rows, multiple attempts per source, old archives, public-v14 restore validation and disabled worker. Verify no provider attempts or jobs are created. Existing local attempts and their protections must remain effective after fencing. The gate test does not establish any of these integration guarantees.

## Minimal implementation path

1. Add `category_assistance."PortableReviewProtections"` with `Actor` (C collation, max 450), `AttemptId` (opaque UUID), `Location`, `Description`, `ItemCodeKey` (C collation, empty code as in attempts), `State`, `Revision`, `ExcludedItemIdsJson`; primary key `(Actor, AttemptId)`, state check and source index. There is deliberately no attempt FK. Introduce an EF entity, mapping, DbSet, migration and model snapshot. Retain all existing attempt-backed rows; the table holds detached imported decisions. Backfill is not necessary unless a migration chooses to consolidate ownership.
2. Add candidate-only disposition and detached-review records to the `PortableTaxonomyArchive.State` and required SQLite archive table. Export dispositions including database `Id` and current operation record, plus the detached protections and a projection of every attempt-backed preference joined to its attempt. Sort exclusions and validate without creating synthetic attempts. Where local and detached copies have the same key, accept only exact equality. Read required fields strictly and validate item IDs against the archived receipt-item identities without requiring current source equality. Enforce all identity and source constraints before any mutation.
3. During candidate preflight, read destination disposition rows, current-operation evidence, detached protections and attempt-backed preferences while holding the write gate; reject divergent keys and ID, source-hash or operation-ID collisions, while retaining unrelated local rows. Append missing rows inside the existing restore transaction. Historical disposition writers now acquire the gate before operation/source locks; assistance preference writers already take it before the attempt lock. Destination idempotence logs must remain valid: export and validate all disposition operations, or reject operation IDs colliding with any retained operation and explicitly define the older-retry boundary. The first option preserves the current API's replay contract.
4. In `HistoricalApprovedMappingExecutor.ApplyChunkAsync`, query detached protections matching normalized source alongside the existing joined preferences and apply the same state/exclusion predicate across all actors. Update `OrganizationDiscoveryStore` and `OrganizationDiscoveryTriggers` to conservatively suppress/dirty detached sources as well. Neither surface may create or dispatch suggestions. Keep group dispositions actor-private as today.
5. Add authenticated, actor-scoped list/get/update operations for detached protections, with source, state, revision and exclusions; update under the write gate using compare-and-swap and a durable operation-id replay record. List these on the existing review workspace as saved decisions, not suggestions, and offer reopen/removal of exclusions using the saved revision. Once reopened, retain the row and revised state so export and replay cannot resurrect an older decision. Update the OpenAPI spec first and regenerate the client. Existing suggestion APIs remain tied to live attempts.
6. Integration-test a real SQLite candidate archive through a fresh PostgreSQL destination and a pre-existing destination. Assert no attempts or jobs are added; state, version and exclusions survive; source-wide executor protection holds for other actors; the owner can reopen; and incompatible destination state, forged archive fields and concurrent edits fail atomically. Test public v14 restore and the disabled worker separately. Until these pass, the gate change alone does not provide portability.

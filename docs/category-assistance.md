# Category assistance persistence

Category assistance is a deployment-wide, opt-in service. Configuring credentials does not enable it. Any active Admin may change consent and limits; eligible saves come from authenticated receipt writers. Manual category choices and approved exact-source mappings take precedence.

A registered background worker processes eligible saves and explicit historical requests. Administrator settings control consent and deployment-wide daily and pending limits. New installations default to 100 requests per UTC day; the daily limit can be set from 1 to 5,000. Unlimited requests are not currently supported. Existing administrator-set limits are preserved on upgrade. The category workspace exposes manual selection independently of provider availability; suggestion and historical-request controls require a configured provider and consent. A strong match is written automatically when the administrator setting **Apply strong matches automatically** is on (the default once consent exists); every other result requires explicit acceptance. Remembering an exact-source mapping is always a separate action. See [the Jev adapter](jev-suggestion-adapter.md) for exactly what is automatic.

## Dispatch evidence

Before downgrading the daily-limit migration, an Admin must lower any configured daily limit above 100 to 100 or less. The migration refuses to downgrade while a higher limit remains configured.

Trusted post-consent, no-choice save observations and explicit, bounded historical requests can enroll an attempt. Historical requests accept at most 25 selected groups with at most 100 purchases per group; they preserve an operation ID for recovery and never silently scan or submit all history. Exact normalized store, description and optional item code are compared alongside the source hash; deduplication also includes taxonomy, provider/model, question policy, settings revision and deployment generations. The provider receives the description and taxonomy, not receipt payment or account details.

A policy version is compiled into each process. When deploying a different question policy, stop all old API and worker processes before starting any new ones; overlapping versions can each treat their own policy as current. Unattempted observations may be processed by the new policy. An existing attempt is retained and is not resent solely because the policy changed. Obsolete attempts do not occupy pending capacity or provide current suggestions.

Queued claims use bounded leases and deferral. Dispatch start atomically checks current consent, source and receipt/item revisions, assignment, mapping, taxonomy and connection state, then debits the deployment-wide UTC-day allowance. A dispatched attempt is never automatically resent after an uncertain outcome. Completing an attempt never assigns a category or approves a mapping. A separate pass of the worker then takes one completed suggestion at a time, rechecks consent, the automatic-write setting, connection, taxonomy and every purchase's eligibility under the classification write locks, and writes strong matches through the shared classification path. That attempt moves to `applied`, leaves the review queue and no longer counts against the pending limit.

Every settings save starts a new settings revision. Queued, suggested and abstained attempts from the earlier revision can no longer be decided, so the save marks them `stale`: they leave review and stop counting against the pending limit. Saves recorded before the settings save are not dispatched. The next save of a source after it is asked again, even when the source had an earlier result. At the pending limit new sources wait, but a save of a source that already has a current attempt still attaches to it.

## Connection and restore fences

Assistance has its own persisted connection generation, independent of the ChatGPT normalization connection. The selected transport must bind to the captured generation and check it immediately before sending. Dispatch start is the authorization boundary; revocation may overlap an already-started request, whose stale result must be discarded at completion.

Portable import disables consent, rotates assistance restore and connection generations, invalidates outstanding work and records the transition in the import transaction. Failed import rolls the transition back. Daily usage survives portable restore. Operational settings, connection state, attempts and usage are excluded from portable archives; approved mappings and classification history remain portable. Automatic Jev activity entries (`JevSuggestionV1`) are deployment-local like the attempts they come from, so they are not archived and cannot be undone after a restore; the `jev` assignments themselves, with their evidence, are archived with the rest of classification history. A restore keeps the destination's own Jev activity entries.

Downgrading the dispatch schema refuses to erase existing attempts or daily usage. Raw PostgreSQL restores are supported through the controlled Compose procedure in `scripts/restore.cs`. It stops the app before reading or replacing the database, writes the current daily usage ledger to a separate CSV beside the dump, restores with checked gzip decompression and PostgreSQL error stopping, then reconciles before starting the app. Reconciliation uses the same lock order and transition as the portable fence: it disables consent, rotates settings, restore and connection generations, marks active attempts stale or indeterminate, clears their results and leases, and appends a settings audit. For each UTC day, it retains the larger of the captured and restored usage counts. The saved CSV must be protected and retained until recovery is verified.

On any failure before restart, including a failed app stop, dump, schema check, ledger read or reconciliation, the script exits without starting the app. If restart fails, it tries to stop the app again and reports whether that stop succeeded. If the restored image predates the assistance schema, apply migrations while the app remains stopped, then run `dotnet run scripts/restore.cs -- --reconcile <saved-ledger.csv>`. This path repeats the fence and usage merge before starting the app. A fresh disaster recovery with no surviving ledger may use `--reconcile` without a CSV after migrations; it disables consent and exhausts the current UTC day's maximum allowance at 5,000. Usage history is then uncertain. Recover an authoritative out-of-image ledger or wait until its unknown days have passed before an Admin considers re-enabling assistance.

Direct `psql`, volume replacement and other restore paths bypass this procedure and cannot be inferred from database generations. Keep the app stopped and run the reconciliation command with the best surviving ledger before use. No automatic detection of arbitrary rollback is claimed.

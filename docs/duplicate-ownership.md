# Duplicate detection and acceptance ownership

`DuplicateDetectionPolicy` in Application owns exact/normalized location grouping and inclusive decimal total tolerance. Total-based groups are anchored at their lowest total (receipt ID breaks ties), then consume nearby receipts in that stable order. Proximity is intentionally not transitive: totals 10, 11, 12 at tolerance 1 yield {10, 11}, not {10, 11, 12}. This corrects the old dependency on unspecified database row order. Exact date/location groups retain their distinct contract and do not compare totals.

`DuplicateAcceptancePolicy` owns canonical unordered pairs, complete all-pair acceptance, and connected components for the accepted-groups screen. Connectedness does not imply full acceptance. Components use iterative traversal and hash-set membership; long chains do not recurse or repeatedly scan member lists. A component exposes every member ID for undo, including soft-deleted receipts, while its visible receipt list includes active receipts only. Undo removes precisely the submitted pairs, never an expanded connected component.

`AcceptDuplicateGroupCommandHandler` owns deduplication, canonical-pair construction, the operation timestamp, and rejection of missing receipts. `IDuplicateAcceptanceStore` is an atomic write port: its adapter opens a transaction, locks submitted receipt rows in a global order, checks active existence, and inserts pairs using PostgreSQL `ON CONFLICT DO NOTHING`. A typed result returns actual inserted count or missing IDs. Missing admission commits no pairs. Locks remain held through commit and are shared with receipt-fact mutation coordination. The nonrelational test fallback is not evidence for concurrency.

`DuplicateReportReader` implements narrow EF projections. SQL remains in Infrastructure; grouping and pair decisions call Application policies. The health badge uses projected date/location group and accepted-pair cardinalities with the same complete-acceptance rule, so accepting a group removes its default-mode warning. It does not hydrate receipts or compute financial totals for a badge. `ReportService` retains other financial read projections and no longer exposes duplicate workflows or acceptance writes.

The public routes, response schemas, pair canonical ordering, active-pair unique index, and soft-delete/reaccept history are unchanged. Accepted-pair curation remains intentionally excluded from generic audit logs. Acceptance lifecycle after receipt facts change is specified by the receipt-fact invalidation workflow; trash/restore alone preserves its established pair history.

Verification covers stable seed grouping, inclusive thresholds, exact versus normalized locations, full versus partial pair coverage, complete hidden-member undo, real PostgreSQL idempotent concurrent writes and lock order, and badge SQL translation. A focused dependency test prevents duplicate command handlers from returning to reporting interfaces.
